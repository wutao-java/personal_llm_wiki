### 1.1 目的

本文记录已经确认的前后端技术路线、真实数据接入边界、接口形态、持久化方式、
实施切片和验证门槛。产品价值、功能范围和验收语义仍由 PRD 与产品 Spec 管理；
本文不扩大 MVP 范围。

### 1.2 本轮锁定的关键边界

1. 内置 Markdown 必须作为资料管理中的真实 `Source` / `SourceVersion` 导入，
   可在产品中打开、阅读、查看版本和追溯引用，不能只把知识快照或图谱加载到前端。
2. 预置知识快照和图谱允许由 Codex 预编译后导入，但必须通过正式后端接入层写入同一对象模型；
   页面不得直接读取预置 JSON 形成第二套状态。
3. 用户后来上传 Markdown 时，必须真实创建来源版本并调用当前已验证的在线服务完成编译；编译阶段、计数、
   警告、失败和发布状态都来自持久化任务，不使用定时器伪造进度。
4. MVP 保留 DeepSeek 并增加一条 OpenAI 兼容在线服务配置。知识编译和知识问答共用当前已验证配置。
5. 本地模型配置只交付完整、精美、双主题适配的前端形态，明确标注“当前版本暂未接入本地模型”；
   不保存为可运行配置、不调用后端、不提供可点击的假连接测试，也不纳入连接验证。
6. 除上述本地模型边界外，所有 P0 操作都必须连接真实服务、持久化真实状态并通过自动化或旅程测试。
7. 用户可见产品名统一为 `FF - LLM Wiki知识库`；实现使用批准标志源文件，实际出现的脚标或研发署名统一为 `@2026 赋范空间 独家自研`。

### 1.3 Windows 个人版技术修订（v1.0.4）

本节覆盖下文冲突的 macOS Keychain、启动自动 seed、仅文本 PDF 和库/环境现状叙述；未改变的 REST/SSE、SQLite、React/FastAPI、同源引用等决策继续有效。

- 使用 Windows、Python 3.12（uv 锁定）和 Node.js 24/pnpm 11。个人数据库默认位于 `data/personal/`，与旧企业回归数据库 `data/app.db` 分离；首次迁移后创建空项目和设置，不自动装载企业 fixture；fixture 导入仅通过同时启用测试模式与 `LMWK_SEED_FIXTURE=true` 执行。无快照时 bootstrap 返回空计数/空快照，编译可从第一份资料创建快照，问答不得对不存在的快照生成。
- 导入表单的自由专题作为来源 `domain`；编译证据传递专题，单一引用专题的知识由证据确定 `domain`，跨专题引用时仅接受模型选择被引用的专题，不允许模型另起专题。发布的知识页和图谱领域从快照数据动态派生，不预设 Java/Python/Agent 封闭枚举。显式企业 fixture 仍使用其原始领域元信息。
- M1 文本 PDF 用 pypdf 按物理页提取，来源版本保存逐页字符区间，证据保存可空页码；旧证据页码为空，不回填猜测值。`0003_pdf_page_provenance` 在已存在列时跳过新增，以兼容旧 `0001_initial` 依据当前 ORM 建表的历史行为；旧 `0002` 数据保持原文。原件读取受当前项目、数据目录及 SHA-256 校验限制，PDF 原件浏览与提取文本阅读分开。
- 凭据使用 keyring 对接 Windows Credential Manager，验证保存、读取、替换和不可用错误；数据库只留引用，响应/日志不含密钥。清理 macOS 专用提示。真实 DeepSeek 调用需单独限制请求和预算，M0 不发起真实调用。
- `.docx` 结构化读取标题、段落及表格；旧 `.doc` 根据 PRD v0.3.6 不在个人版范围，不提供转换器。PDF 逐页优先 pypdf，仅无文本或低质量页尝试本机渲染和 Tesseract 中文/英文 OCR。Windows OCR 可执行文件、语言包、版本、许可及分发方式未探测成功前不得声称支持；缺依赖须显式报错。OCR 受文件大小、页数、超时和资源限制，不调用第三方 OCR。
- 扫描 PDF 仅在单页可提取文本不足且存在图像/图形内容时触发 OCR：项目锁定 `pypdfium2` 5.13.0 + Pillow 12.3.0，按整页渲染并限制物理页数、像素和文本量；不采用需要另行审查 AGPL 的 PyMuPDF。已在 Windows 项目忽略的 `data/toolchain/ocr` 隔离目录安装/验证 Tesseract 5.5.3 与 `eng`/`chi_sim` 语言数据；默认读取此项目本机目录，也可由 `LMWK_OCR_EXECUTABLE`、`LMWK_OCR_DATA_DIR` 覆盖。受限临时文件、子进程超时与隔离环境防止密钥传递。逐页 OCR TSV 汇总置信度；低于 65 分或不足 40 个非空白字符的页面保留原始识别文字和分数，来源版本进入 `needs_review`，不为该版本创建编译任务或问答证据。即使整页识别文字为空，也可从资料侧栏填写。`POST /api/v1/source-versions/{source_version_id}/ocr-review` 必须一次提交全部待复核页、每页不少于 40 个非空白字符；提交后重算页字符区间，标记 `reviewedAt`，保留原始机器分数和不可变 PDF 原件，再创建正常编译任务并进入审核发布。缺执行文件/语言包、渲染或 OCR 超时等处理错误仍整份导入可见失败。已通过隔离中英文高可信及低质量页复核的 Edge 引用旅程；工具链未随源码分发，部署到其他 Windows 机器需单独安装与核查许可证。
- M2 `.docx` 由项目锁定 `python-docx` 1.2.x 解析，先限制 OOXML ZIP 条目数与展开体积，再按文档正文顺序提取标题、段落及表格行。`0004_word_block_provenance` 在来源版本保存内容块字符区间/标签，在证据保存可空内容块编号和标签；旧证据不猜测段落。原始 DOCX 字节不变，下载接口校验数据目录与 SHA-256；引用导航指向提取块。扫描 PDF 本机 OCR 和低质量页复核已在当前 Windows 机器完成隔离验证，跨机器依赖与许可仍待核查。
- 提取结果保留 `sourceVersionId`、原文哈希、页码/段落和提取方式/质量标记；低质量页待复核，不向确定性问答提供未核对证据。M1 验证 Markdown/文本 PDF，M2 分别验收 `.docx` 和扫描 PDF；不接受手工预转换替代格式验收。
- 现有前端实际使用 `3d-force-graph` + Three.js，与旧版 TD-12 描述的 `react-force-graph-3d` 不一致。M0 保留运行现状并记录差异，图谱实现变更另行评估；不为文档一致性无测试地更换渲染库。
- F-06 问答质量使用独立一级路由 `/answer-quality`，旧 `/sources/quality` 重定向至此；页面从真实 `Answer`、问题消息、引用和知识快照读取分页记录；`0007_answer_reviews` 以 `answer_id` 为主键持久化单用户人工核查，不改写原始回答或引用。汇总仅计数已存状态（完成、失败、证据不足、完成但无引用、人工核查），不把机械状态当作事实正确率。检索命中和上下文证据覆盖因历史回答未保存有序检索与完整上下文而不反推；题集及同条件对比留待专门设计。

## 2. 架构决策

| ID | 已确认决策 | 原因与边界 |
|---|---|---|
| TD-01 | 采用本地优先 Web 应用 | 首版用浏览器即可完成展示和开发；不增加 Electron/Tauri 打包复杂度。 |
| TD-02 | 开发期前后端分离运行，交付期由 FastAPI 提供前端静态资源 | 开发体验清晰；交付保持同源访问，减少跨域和双进程使用成本。 |
| TD-03 | 前端采用 Node.js 24 LTS + pnpm 11，应用使用 React + TypeScript + Vite | 适合复杂状态、精细交互、模板组件化和快速迭代。 |
| TD-04 | 后端采用 Python 3.12 + FastAPI + Uvicorn | 与 DeepSeek 调用、Markdown/PDF 处理和轻量编译流程匹配。 |
| TD-05 | 不采用 LangChain、LangGraph、GBrain 等编排框架 | MVP 编译步骤固定且可直接表达，优先保证可观察性和可维护性。 |
| TD-06 | 主存储采用 SQLite（WAL）+ SQLAlchemy 2 + Alembic | 单机数据量适配，事务、迁移、全文检索和备份路径清晰。 |
| TD-07 | 原始来源与生成的 Markdown 文件存放在项目数据目录，数据库保存身份、状态和路径 | 保留不可变原始字节与可读产物，避免把大段文件内容混成组件状态。 |
| TD-08 | 编译任务采用单进程持久化队列和后台 worker | 不引入 Celery/Redis；页面刷新后仍能恢复真实任务状态。 |
| TD-09 | 任务进度和问答流式结果采用 SSE，其他能力采用版本化 REST API | 支持单向实时状态，协议简单，错误与重连语义明确。 |
| TD-10 | 真实接入 DeepSeek 和一条可切换的 OpenAI 兼容在线服务；本地模型只做前端展示 | 两条在线配置分别验证，避免把未实现连接伪装为可用能力。 |
| TD-11 | 检索采用 SQLite FTS5 trigram + BM25 + 一跳关系扩展 | 首版不引入向量数据库，仍能支持中文资料、证据定位和图谱上下文。 |
| TD-12 | 图谱采用 `react-force-graph-3d` + Three.js | 可复用已选 3D 模板的力导向、光效、粒子和相机逻辑，不重写完整渲染层。 |
| TD-13 | Markdown 采用 `react-markdown` + GFM + HTML 清理 | 满足知识页和来源页的专业阅读，同时阻止不可信主动内容执行。 |
| TD-14 | P0 PDF 只支持可提取文本，不包含 OCR | 控制首版链路；扫描件明确返回不支持原因。 |
| TD-15 | 包版本在脚手架创建时解析当前稳定版本并写入锁文件 | 技术计划锁定职责和依赖类型，不在实现前预先写死具体小版本。 |
| TD-16 | 品牌源资产保存在 `docs/assets/brand/ff-llm-wiki-logo.png` | 源文件作为不可改写视觉基线；前端发布副本不得改变构图、颜色或比例。 |

## 3. 总体运行结构

```text
浏览器
  └─ React 单页应用
       ├─ 知识问答 / 来源引用
       ├─ 资料管理 / 编译状态
       ├─ Markdown 知识与来源阅读
       ├─ 3D 知识图谱
       └─ 在线模型与外观设置
              │ REST + SSE
              ▼
FastAPI 应用
  ├─ API 路由与 Pydantic 契约
  ├─ 来源服务 / 预置数据导入服务
  ├─ 编译任务服务 + 单进程 worker
  ├─ 快照发布 / 图谱投影 / Wiki 服务
  ├─ FTS5 检索 / 证据整理 / 引用校验
  ├─ DeepSeek / OpenAI 兼容客户端
  └─ 设置与密钥引用服务
       ├─ SQLite + FTS5
       ├─ 不可变来源文件
       ├─ 生成 Markdown 文件
       └─ Windows Credential Manager 中的独立在线服务凭据
```

### 3.1 进程边界

- 开发：Vite 开发服务器与 FastAPI 分别运行；Vite 代理 `/api` 到后端。
- 本地运行：先构建前端，再由 FastAPI 提供静态资源和 `/api/v1`，浏览器只访问一个本地地址。
- 后端以一个应用进程和一个进程内 worker 完成 MVP。编译任务先落库再执行，不能只存在内存中。
- MVP 不包含账号、云部署、多租户、多进程任务调度、Redis、图数据库和向量数据库。

## 4. 前端技术方案

### 4.1 基础栈

| 能力 | 采用方案 | 使用边界 |
|---|---|---|
| 运行时与依赖管理 | Node.js 24 LTS、pnpm 11 | 在 `packageManager` 和 lockfile 中锁定；不混用 npm/yarn 锁文件。 |
| 构建与语言 | Vite、React、TypeScript | 严格类型；不使用运行时拼接的第二套数据模型。 |
| 路由 | React Router | 六个一级模块有稳定路由；详情与返回位置可恢复。 |
| 服务端状态 | TanStack Query | 查询、缓存、失效、后台刷新；任务真相仍在后端。 |
| 短期界面状态 | Zustand | 侧边栏、图谱相机/选择、草稿、详情面板和返回上下文。 |
| 无障碍基础控件 | Radix UI Primitives | 只使用行为和可访问性能力，视觉完全由项目主题控制。 |
| 动效 | Motion + CSS transitions | 页面和面板过渡；Three.js 内部动效由图谱层管理。 |
| 样式 | CSS Variables + CSS Modules | 建立项目语义 token；不使用 Ant Design 或 MUI 作为主视觉层。 |
| Markdown | react-markdown、remark-gfm、rehype-sanitize | 知识页与来源预览共用安全渲染管线。 |
| 图谱 | react-force-graph-3d、Three.js | 由 `GraphProjection` 适配，不直接读取内置数据 JSON。 |
| API 类型 | OpenAPI schema + openapi-typescript | 后端契约生成前端类型，禁止手写漂移副本。 |
| 测试 | Vitest、Testing Library、Playwright | 组件逻辑、跨页状态和双主题核心旅程。 |

### 4.2 视觉实现原则

- 从 `chatbot-frontend-templates-pack` 的 RAG 引用模板复用对话结构、流式呈现、引用聚焦、
  来源卡展开和共享交互层；把示例回复和非生产钩子替换为真实 SSE 问答服务。
- 从 `knowledge-graph-viz-pack` 的 3D 图谱模板复用场景初始化、节点光效、关系粒子、
  镜头聚焦和稳定布局逻辑；将模板数据入口收口为一个 `GraphProjectionAdapter`。
- 模板名只作为代码来源说明，不进入页面。用户只看到“知识问答”“资料管理”“知识页面”
  “知识图谱”和“设置”等专业名称。
- Apple 启发方向落实为排版、层级、留白、材质、焦点和动效质量；不能据此删除问答与图谱的
  关键视觉效果，也不能复制 Apple 品牌素材。
- 明暗主题共享语义 token，但分别调校图谱画布、节点核心、光晕、边、标签、来源高亮和内容面。
- `prefers-reduced-motion` 与产品中的“减少动态效果”同时生效；减少运动后保留选择、聚焦和证据能力。
- 展开侧边栏显示批准标志和完整产品名 `FF - LLM Wiki知识库`；收起状态只显示标志并提供标准无障碍文本。
- 明暗主题使用同一个黑底白图品牌源文件，不对位图做反色、重绘、裁切或光效加工；具体外层间距和边界遵循 `docs/design/brand.md`。
- 浏览器标题、启动和错误恢复界面不得暴露仓库名 `LlmWikiKnowledge` 或旧缩写 `LMVK`。

#### 4.2.1 图谱可读性实现补充（2026-10-03）

- 延续实际 `3d-force-graph` + Three.js 实现和 `GraphProjection`，不新增依赖、节点、关系或后端字段。自动旋转默认关闭，仍保留手动开启、关系流动和减少动态效果。
- 节点名称投影为可点击 DOM 标签，每 100 ms 刷新；优先选中、搜索命中和直接邻接，避让其他标签、顶部控件、图例和计数。最多显示 16 条；无枢纽时按真实度数选取前 8 个候选，空间不足时减少显示数量，不改变枢纽标记。
- 节点或关系选择优先于途经悬停，持续弱化无关对象；有向的聚焦关系显示方向箭头。标签、节点、边、粒子、图例及详情统一使用同一领域显示颜色；浅色仅将 `#65a30d` 校准为 `#629f0d` 以通过对比门槛，后端颜色不变。
- 聚焦按真实邻域的相机空间边界计算距离，保留当前观看方向；桌面为详情预留画布宽度，手机为底部详情预留高度。电荷力使用 `strength(-42)`、`distanceMax(180)`，连边距离为 72，并在预热前设置，避免孤立节点过度散开。
- 深色后处理顺序为已有 `RenderPass`、`UnrealBloomPass(0.65, 0.35, 0.4)`、`OutputPass`；显式设置场景背景，销毁时清理新增 pass。浏览器检查实际画布像素，深色底色应接近 `[4, 6, 13]`，浅色应接近 `[247, 250, 251]`，不能仅以 WebGL 调用计数证明显示正常。
- 验收分别使用显式隔离的密集回归数据和个人现有稀疏图谱；主题写入仅发生在隔离服务，个人浏览器验证仅允许 GET API 请求。记录桌面 1440 × 900、手机 390 × 844 的双主题画面、选中名称持续可见、实际关系数、避让和阅读联动。

### 4.3 前端状态所有权

| 状态 | 唯一真相 | 前端职责 |
|---|---|---|
| 来源、知识、关系、快照、编译任务 | FastAPI + SQLite | 查询、显示、失效缓存，不自行制造状态。 |
| SSE 当前事件 | 后端事件流 | 合并到对应查询缓存；断线后按 `lastEventId` 或任务查询恢复。 |
| 主题偏好、减少动态效果 | 后端偏好 + 首屏本地镜像 | 首屏防闪烁，保存后全局应用。 |
| 路由与选中对象 | URL + Zustand | 支持深链接与返回原上下文。 |
| 图谱相机和临时交互 | Zustand / 图谱实例 | 不写入知识对象，不影响 `GraphProjection` 语义。 |
| 本地模型表单 | 纯前端展示状态 | 不创建可运行配置、不测试连接、不参与编译或问答。 |

### 4.4 本地模型界面边界

本地模型分区用于呈现未来接入形态，必须满足以下约束：

- 展示连接名称、服务地址、模型标识等专业字段和完整双主题状态。
- 在分区顶部持续显示“当前版本暂未接入本地模型”。
- “测试连接”“设为默认”等会暗示真实能力的操作不提供，或以不可操作状态配合明确原因显示。
- 表单变化只保留在当前前端会话；不写入后端 `ModelProfile`，不显示“保存成功”或“连接成功”。
- DeepSeek 配置和本地模型展示采用清晰分区，不能让用户误认为两者具有相同实现状态。

## 5. 后端技术方案

### 5.1 基础栈与模块

| 能力 | 采用方案 |
|---|---|
| 运行时与依赖管理 | Python 3.12、uv |
| Web/API | FastAPI、Uvicorn、Pydantic v2 |
| 数据访问与迁移 | SQLAlchemy 2、Alembic、SQLite WAL |
| 外部调用 | httpx 异步客户端 |
| 凭据 | keyring 调用 macOS Keychain；数据库只保存引用和掩码信息 |
| PDF 文本提取 | pypdf；只处理可提取文本 |
| 测试与静态检查 | pytest、pytest-asyncio、Ruff |

当前机器已具备 Node.js 24、pnpm 11 和 uv；系统 `python3` 仍为 3.9，
因此后端必须由 uv 创建并锁定 Python 3.12 环境，不能直接使用系统 Python 运行或安装依赖。

建议按职责组织后端，而不是按页面复制业务逻辑：

```text
backend/
  app/
    api/              # /api/v1 路由和 SSE
    core/             # 配置、错误、日志、生命周期
    db/               # 模型、会话、迁移入口
    contracts/        # Pydantic 输入输出契约
    services/         # 来源、编译、快照、检索、问答、设置
    workers/          # 持久化任务执行器
    adapters/         # DeepSeek、文件、Keychain、PDF
  tests/
```

目录是实施基线；如脚手架阶段发现现有模板要求不同，可在不改变职责边界的前提下小幅调整。

### 5.2 轻量编译执行器

编译器使用明确的 Python service 和阶段函数，不引入通用 Agent 图编排框架。每个阶段：

1. 接受类型化输入并返回类型化结果；
2. 进入阶段前更新 `compile_runs.stage`；
3. 完成对象后累计真实计数；
4. 将可恢复失败记录到具体来源或对象；
5. 产生持久化事件供 SSE 重放；
6. 只有一致性校验和人工接受完成后才原子发布新快照。

任务进程异常退出时，未完成运行标记为 `interrupted`。再次启动后页面显示可恢复状态，
由用户选择继续重试，不能自动把任务显示为成功。

### 5.3 在线模型接入

- 使用一个轻量的 OpenAI 兼容 HTTP 适配器，不引入模型框架。
- 保留现有 DeepSeek 配置及 `/settings/deepseek` 接口；新增固定的 OpenAI 兼容配置和
  `/settings/models` 列表、保存、测试、激活接口。复用 `ModelProfile` 和
  `AppPreference.default_model_profile_id`，旧库首次读取时创建未配置的兼容项，无需迁移表结构。
- 兼容服务接受不含凭据、查询串和片段的 HTTP 或 HTTPS API 根地址，DeepSeek 仍仅接受 HTTPS；HTTP 会明文传输 Bearer 凭据、提问和资料片段。兼容服务支持 `POST /chat/completions` 的非流式文本与
  流式 SSE；连接测试以最小非流式请求验证所填模型，可能产生少量费用，不依赖 `/models`。
  编译依赖提示词和本地 Pydantic/证据校验，不强加各兼容服务未必支持的 JSON 模式和采样参数。
  只通过测试的配置可激活，切换不修改旧快照及回答。
- `POST /settings/models/{profile_id}/discover` 用受校验的表单地址和草稿凭据（或已保存凭据）请求 `GET /models`，
  只返回合法模型标识，不持久化草稿；不支持列表的兼容网关可手动添加模型。保存在线配置时持久化模型列表及所选默认模型，
  旧库通过迁移将原单模型加入列表；问答框读取已保存列表并按次传 `profileId` 和 `modelId`，
  服务端仅允许已验证且有凭据的配置，回答持久化服务与模型以便失败重试；旧请求未指定时仍使用默认配置。
  `answers.model_profile_id` 通过增量迁移添加；知识编译始终使用当前全局配置。
- `baseUrl` 与 `modelId` 均由配置提供；实现不能把可能变化的模型标识散落硬编码在业务代码中。
- 开发环境的推荐非敏感默认项为 `https://api.deepseek.com` 与 `deepseek-v4-pro`；设置页通过获取或添加模型维护列表并选定编译默认项，
  后端只从当前已验证配置读取它，不使用已经停用的历史别名。
- 连接测试调用 DeepSeek 的真实模型列表或最小可计费请求，返回经过整理的状态、耗时和错误类别。
- 编译结构化输出使用 JSON 输出约束、Pydantic 校验和有限次数重试；空响应、字段缺失、
  悬空身份或非法引用不能进入候选快照。
- 问答先完成本地检索和证据整理，再把有身份的证据传给当前在线服务；模型返回的引用只能从
  本次允许的 `evidenceId` 集合中选择。
- API Key 只在系统凭据库中存储。请求日志不记录 Authorization、完整提示词、原始文件全文或密钥。
- 编译和问答使用同一个当前在线配置；`CompileRun` 记录所用 `profileId` 和 `modelId`，
  `Answer` 记录所用 `modelId`，更换设置不改写历史事实。
- 开发前由项目根目录 `.env` 提供一次性本地密钥入口；`.env` 必须被版本控制排除并保持仅当前用户可读，
  `.env.example` 只保留空密钥和非敏感默认项。不得要求项目发起人把 API Key 粘贴到对话、文档、日志或提交记录中。
- 后端设置能力完成后，产品内保存的在线服务凭据分别进入 Windows Credential Manager；开发 `.env` 只作为本地启动输入，
  不作为前端配置来源，也不通过 API 回传。

### 6.2 文件数据目录

运行数据目录与仓库内置数据目录分离，至少包含：

```text
data/
  sources/<sourceId>/<sourceVersionId>/original
  extracted/<sourceVersionId>.json
  wiki/<snapshotId>/<knowledgeId>.md
  projections/<snapshotId>.json
  app.db
```

- `original` 写入后不可修改；内容变化创建新的 `sourceVersionId`。
- Wiki 与 projection 都是可再生产物；其丢失不能导致原始来源或数据库事实丢失。
- 运行数据目录和密钥不得提交到版本库。

## 7. 内置知识数据接入

### 7.1 一次性初始化

第一次启动且内置知识项目不存在时，后端执行一个幂等 seed importer：

1. 校验 `fixtures/enterprise-customer-service/corpus-manifest.json` 和来源 SHA-256；
2. 通过与 HTTP 上传共用的来源 repository/service 导入 66 个逻辑来源和 72 个不可变来源版本；
3. 保留来源文件名、版本、状态和原始 Markdown，使其完整出现在“资料管理”；
4. 通过正式快照 importer 读取 `preset/default.json` 指向的 `KS-RETAIL-SERVICE-1.1`；
5. 导入 150 个知识项、450 条关系和 1112 个证据片段；
6. 校验每个证据都指向已导入的 `SourceVersion`，并生成/验证同快照图谱投影和 Wiki；
7. 原子设置项目当前快照并记录 seed 版本。

如果项目已存在，初始化不重复执行，不覆盖用户数据，也不把当前快照退回默认快照。
seed importer 不直接写组件 JSON，不绕过 repository/service 的身份与一致性校验。

### 7.2 产品可见结果

- “资料管理”首屏真实显示 66 个逻辑来源；版本汇总能够对账 72 个来源版本。
- 用户可打开当前或历史 Markdown 版本，使用与上传来源相同的安全阅读器查看全文。
- 任一知识页面、图谱节点、关系或回答引用都能经 `evidenceId` 回到这些已入库资料。
- “知识图谱”读取由 `KS-RETAIL-SERVICE-1.1` 生成的 `GraphProjection`，不从内部数据文件直连前端。
- 预置 40 个问题只能作为评测或推荐候选；提交后仍执行真实检索、DeepSeek 生成和引用校验。

## 8. 用户上传与真实编译链路

```text
上传 Markdown
  → 校验文件与重复内容
  → 写入不可变 SourceVersion
  → 提取可定位证据片段
  → DeepSeek 生成结构化知识候选
  → 建立关系并绑定证据
  → Pydantic 与身份一致性校验
  → 展示轻量审核摘要
  → 用户接受
  → 原子发布 KnowledgeSnapshot
  → 重建 Wiki、GraphProjection 和 FTS5 索引
```

### 8.1 可见阶段与真实计数

| 阶段代码 | 产品文案 | 必须来自后端的计数/结果 |
|---|---|---|
| `validating` | 正在校验 | 文件总数、通过、重复、失败 |
| `importing` | 正在导入 | 已写入来源版本数 |
| `extracting` | 正在读取 | 已读取来源、片段、失败 |
| `compiling` | 正在生成知识 | 已处理片段、知识候选、新增、更新 |
| `relating` | 正在建立关系 | 关系候选、有效关系、警告 |
| `validating_result` | 正在校验结果 | 悬空身份、缺少证据、冲突、失败 |
| `awaiting_review` | 等待确认 | 可接受、待处理、警告、失败 |
| `publishing` | 正在发布 | Wiki、图谱投影、检索索引状态 |
| `completed` | 已完成 | 新快照和最终对象数量 |
| `failed` / `interrupted` | 处理失败 / 处理已中断 | 失败阶段、对象和可恢复动作 |

- 不显示模型无法提供的虚假精确百分比；使用当前阶段、对象计数和已完成步骤表达进度。
- SSE 断开不取消任务。前端重连后先查询 `CompileRun`，再从最后事件序号继续。
- 单个来源失败不阻止其他来源进入候选结果；发布范围必须在审核摘要中明确。
- 新快照发布前，旧快照仍可读，但界面显示“知识更新处理中”及上次发布时间。

### 8.2 全文分批与更新一致性

- `_split_evidence` 保留全部非空正文段落并按 1200 字符继续分割长段，不设最小段长或固定段落总数上限；PDF 页及 DOCX 内容块边界优先切分，字符区间与提取正文一致。新证据身份为 `E-{sourceVersionId}-C{charStart}-{charEnd}`，不覆盖历史 `P` 编号证据。
- 引用证据不变，生成输入另按同级标题和显式问题边界分组，子标题及解释尽量留在所属组；代码围栏内不识别标题/问题。缺少明确结构时按原文段落组批，不用额外模型预切分。每批默认最多 6 组、12000 字符的估算输入预算（包括证据标签和已有知识），不再设置证据片段数量上限；超预算组仅在证据边界继续分批并带上所属标题。字符预算是保守估算，不宣称等同于服务商 token 上限。输出要求简洁保留事实与必要示例，不逐段复写原文；完整原文和全部证据继续保留。
- 编译默认使用 Chat Completions SSE（`LMWK_COMPILE_STREAM=true`），支持服务忽略流式标记返回普通 JSON；不支持流式的服务可显式设为 `false`，不自动重复付费请求探测能力。兼容服务不额外发送 `temperature`、输出上限或推理参数。连接超时默认 20 秒（`LMWK_COMPILE_CONNECT_TIMEOUT`），无网络数据的读取空闲超时 180 秒（`LMWK_COMPILE_READ_TIMEOUT`），单批请求总时限 300 秒（`LMWK_COMPILE_TOTAL_TIMEOUT`），总时限包含接收流与心跳。SSE 仅累积正文；必须收到正常完成原因并通过完整 JSON、证据与关系校验后才能保存断点，不将部分输出当作候选。截断、拒绝或畸形结构不自动重试。
- 每任务默认最多 3 路并发，可用 `LMWK_COMPILE_CONCURRENCY`（1～6）调整；任务内部数据库写入由单一协程串行执行。超时、连接错误、429/5xx 自动退避重试，默认每批额外 1 次。证据引用越界允许一次纠正，与网络重试共用 `LMWK_COMPILE_MAX_RETRIES` 预算；预算为 0、预算已用完或纠正后仍越界时立即失败。其余校验错误与无效凭据不自动重试。取消或失败时清理在途子任务。多个资料任务同时启动时，各自受限，不宣称跨任务总限流。
- 引用纠正请求保留本批全部正文、专题和已有知识上下文，仅将请求内证据标签换为 `E1`、`E2` 等短编号，内容组标签也使用本地短编号；明确告知模型重新整理、只使用本次给定证据，不把失败输出送回或记录正文。知识和关系的 `evidence_ids` 必须精确命中本次映射，再还原原始身份并执行完整校验；不做模糊匹配、不补造或丢弃未知引用。正常请求、分批及断点签名不变，已有有效批次继续可复用；纠正成功仍须全部批次完成并审核后发布。编号映射只验证可追溯性，不代表事实忠实度已验证。
- 成功批次校验后立即写入 `CompileRun.candidate.checkpoint`，其审核数组保持空；断点签名覆盖算法版本、输入证据与专题、批次划分、在线服务地址/模型身份、已有知识上下文和基础快照，不包含凭据。重新处理复制旧断点，只有重新计算签名一致才复用；复用结果仍校验本批证据、专题和已有知识引用。完成后按批次顺序合并并替换为完整审核候选，无新增存储或数据库迁移。
- `batchesTotal`、`batchesCompleted`、`batchesInFlight`、`batchesReused`、`batchesRetried`、`evidenceProcessed`、`knowledgeCandidates`、`relationCandidates` 及读取/生成/最近批次毫秒耗时写入任务和持久化 SSE。在途批次无结果时后端每 5 秒更新真实生成耗时，不增加完成比例或候选数，刷新页面仍可恢复。前端明确展示生成批次完成比例，不再用阶段序号推算任务百分比；输出耗时、首次正文延迟和用量日志不包含凭据、服务 URL 或正文，无法仅据此区分上游排队与推理。
- Alembic 初始化日志使用 `disable_existing_loggers=False` 并保留 `app` 的 INFO 输出，避免迁移后静默关闭模型请求诊断。仅记录成功/失败类别、HTTP 状态、耗时、估算输入字符及服务返回的用量，不记录请求/响应正文；启动迁移后的日志隐私由适配器测试验证。
- 跨批标题采用 Unicode/空白规范化后进行明确同名合并，重复正文不追加，同名不同专题拒绝静默合并；同端点与关系类型的重复关系合并证据编号，关系证据在本批及整体范围分别校验，再整体进入审核。不做模糊语义归并或额外全量模型调用。
- 以变化来源及共同支持当前知识的来源构建受影响连通范围，使用这些来源的当前可编译版本。未复核、移出或过期输入阻止生成；不引入调度框架或新存储。
- 候选保存 `baseSnapshotId` 和 `refreshedSourceIds`；接受时重新校验来源当前版本及知识快照，变化时持久化失败和可重试原因。重试解析当前来源版本，不重复编译已过期版本。
- 原子发布替换受影响页和关系，移除未重新生成的受影响页、引用刷新来源旧证据的边和无效端点；同语义新关系优先替换旧证据。其余当前页及历史快照、证据和原件不改写，FTS5 同事务重建。

## 9. 检索与带引用问答

### 9.1 检索流程

1. 对问题做标准化和关键词提取；
2. 用 FTS5 trigram/BM25 检索当前 `snapshotId` 的知识正文与证据片段；
3. 使用命中知识的一跳关系补充相关知识，但不给无文本证据的关系更高事实权重；
4. 合并、去重并限制证据上下文；
5. 把允许使用的 `knowledgeId`、`evidenceId` 和来源元信息交给 DeepSeek；
6. 校验输出中的每个引用身份和范围；
7. 流式返回正文片段，最终事件返回经过校验的引用和相关知识。

### 9.2 证据不足

如果本地检索没有达到最低证据条件，后端直接返回结构化“当前知识中无法确认”，
可以列出检索范围和建议补充的资料，但不能让模型生成确定性答案或无来源引用。
取得证据后，最终正文必须包含至少一个 `[n]`，且全部编号位于本次有序证据范围：
缺失返回 `missing_answer_citation`，零或越界编号返回 `invalid_answer_citation`，
经现有失败 SSE 与重试链路处理，不保存成功回答。编号校验不等于事实忠实度评估。

### 9.3 会话与历史结果

- 每个问题记录使用的 `snapshotId`；历史答案不随当前快照变化而改写。
- 当前快照变化后，继续旧会话时明确显示知识已更新；新问题使用新快照。
- 推荐问题与当前快照绑定，点击后调用正常问答接口，不按文本命中固定答案。
- 最多读取当前问题之前的 6 条同会话用户问题，每条最多 1000 字符，仅用于指代理解；检索补充使用上一条问题与当前问题，不把历史模型回答当证据。
- `context_knowledge_ids` 仅解析本次回答快照中存在的知识，优先去重后与检索结果合并，最多 8 页及 12 个证据片段。失效选择忽略，新问题仍使用当前快照。
- 候选知识的全部去重证据使用中英文关键词覆盖及逆文档频率本地排序，当前问题权重高于上一条问题；同分保留候选知识顺序，再限制 12 段。不是向量或外部模型重排，全文进入编译不代表所有问题均能召回。
- 回答任务按 answer ID 管理；取消与关停捕获取消信号，保存 failed、`answer_cancelled` / `answer_interrupted`、失败消息及终结 SSE。启动恢复所有非终态回答，补齐历史失败消息；不自动调用在线服务，手动重试仍校验当前配置。对话详情携带活跃回答用于无 URL 参数刷新重连。
- 排序与恢复分别追踪 `AC-F05-08`、`AC-F05-09`，使用中英文末尾证据、取消及启动恢复测试，以及真实 REST/SSE 浏览器重连验证。

### 9.4 完整项目备份（F-07 / AC-F07-01）

- ZIP v1 包含 `project.json` 白名单业务表及 `originals/<sha256>` 原件；不复制在线 SQLite/WAL 文件，不包含 ModelProfile、AppPreference、凭据引用或本机绝对路径。采用逻辑恢复以保留本机配置及事务回滚能力。
- 压缩上传上限 64 MiB，展开上限 256 MiB，最多 4096 条目、100000 行、64 MiB 清单；拒绝额外路径、重复条目、加密、哈希或大小错误、未知表/列、重复身份、缺失来源/证据/关系端点及引用不一致。
- 审核候选按业务字段类型、唯一身份、来源版本与关系端点校验；已发布历史知识允许保留所列同一来源的旧版本证据，不改写冻结数据。终结回答事件必须与保存的回答身份、状态、正文、引用及错误一致，不能通过事件替换历史引用。
- 编译断点属于私有运行数据，备份恢复时校验签名格式、批次哈希与结果结构、本任务输入证据范围及关系端点；断点不能作为可发布审核结果。模型配置不随备份恢复，继续处理时仍按当前配置重新计算签名并校验缓存。
- 导出使用一致读事务；处理中的编译与回答禁止导出/恢复。校验接口仅返回摘要，恢复必须提交 `confirmation=replace`，服务端再次全量校验。
- 单进程 API 的写请求串行化；替换前 `BEGIN IMMEDIATE` 再检查任务，逆依赖删除/正依赖插入白名单表，同事务重建 FTS。原件写入受限、内容寻址的新目录，不覆盖或删除原有原件，数据库失败回滚并清理本次新增文件。只面向可信本机使用，不提供多进程恢复保证。
- 恢复后保留历史编译/问答模型事实，但不恢复可运行服务配置；不得触发重试或凭据测试。
- 前端恢复后重置项目资源查询和草稿/图谱选择，保留模型、外观与工作区启动缓存；启动查询单独失效刷新，避免卸载设置页而丢失完成提示。

## 10. API 基线

所有接口使用 `/api/v1`。错误响应至少包含稳定错误码、用户可理解消息、是否可重试和关联对象 ID。

| 能力 | 方法与路径 | 关键语义 |
|---|---|---|
| 启动状态 | `GET /bootstrap` | 当前项目、快照、偏好、运行中任务和 seed 状态 |
| 来源列表 | `GET /sources` | 分页、筛选、版本与处理状态 |
| 来源上传 | `POST /sources/import` | multipart 上传，返回来源与 `runId` |
| 来源详情 | `GET /sources/{sourceId}` | 逻辑来源和版本列表 |
| 来源内容 | `GET /source-versions/{id}/content` | 只读 Markdown/文本/PDF 提取结果和定位元信息 |
| 编译运行 | `GET /compile-runs/{runId}` | 当前阶段、计数、问题和恢复动作 |
| 编译事件 | `GET /compile-runs/{runId}/events` | SSE，持久化事件、重连和终态 |
| 编译重试 | `POST /compile-runs/{runId}/retry` | 重试失败项或创建新运行，行为显式 |
| 审核摘要 | `GET /compile-runs/{runId}/review` | 新增、更新、警告、失败和影响范围 |
| 接受发布 | `POST /compile-runs/{runId}/accept` | 事务发布新快照；幂等处理重复提交 |
| 知识目录 | `GET /knowledge` | 当前快照搜索、筛选和分页 |
| 知识详情 | `GET /knowledge/{knowledgeId}` | Markdown、关系、来源和版本 |
| 证据详情 | `GET /evidence/{evidenceId}` | 来源版本、定位范围、原文和前后文 |
| 图谱投影 | `GET /graph` | 当前快照节点、边、分组、布局种子和计数 |
| 会话 | `GET/POST /conversations` | 最近对话和新建对话 |
| 推荐问题 | `GET /suggested-questions` | 当前快照候选及失效语义 |
| 提交问题 | `POST /conversations/{id}/questions` | 创建问题，返回 `answerId` |
| 回答事件 | `GET /answers/{answerId}/events` | SSE，真实检索/整理/生成阶段、正文和最终引用 |
| DeepSeek 设置 | `GET/PUT /settings/deepseek` | 非敏感配置和凭据写入/替换，不回显明文 |
| 连接测试 | `POST /settings/deepseek/test` | 真实测试结果、耗时和安全错误 |
| 在线配置与切换 | `GET /settings/models`、`PUT /settings/models/{profileId}`、`POST /settings/models/{profileId}/test`、`POST /settings/models/{profileId}/activate` | 两条配置独立保存和验证，只有可用项可以激活 |
| 外观设置 | `GET/PUT /settings/appearance` | 主题与减少动态效果 |

本地模型不提供 API 路由。若未来实现，必须通过新的产品决策和技术计划版本引入，
不能复用当前前端展示表单并假定其已具备后端能力。

知识及资料目录前端每页 30 项，调用既有 `page`/`pageSize` 包络并使用 `total` 计算边界。
知识目录 `query` 匹配标题、摘要或 Markdown 正文，以路由查询和专题、页码同步；
搜索变化清除旧阅读选择并回到第一页。资料目录页码仅为列表状态，不复用 PDF 的页定位参数。

## 11. 安全与数据完整性

- 上传文件采用允许列表、大小限制、规范化文件名和服务端生成的存储路径；不信任客户端路径。
- Markdown 中的原始 HTML、脚本、事件处理器和危险 URL 在渲染前清理。
- PDF 只读取可提取文本；加密、损坏或纯扫描文件返回明确失败，不调用隐式 OCR。
- 两条在线服务的凭据不进入响应、日志、数据库备份、项目导出或前端持久化存储。
- 来源内容作为不可信数据传给模型；系统提示明确禁止执行来源中的指令。
- 快照发布使用数据库事务。任何知识、关系、证据或索引校验失败时保持上个快照可用。
- 预置数据导入、用户上传和项目恢复都进行身份、哈希、引用与关系端点校验。
- 日志只记录运行 ID、对象 ID、阶段、耗时和安全错误摘要，不记录密钥或完整私有正文。

### 12.2 真实与替身边界

- 单元测试可使用确定性的 DeepSeek HTTP 替身测试异常和结构化输出边界。
- P0 集成验收必须在项目发起人提供 API Key 后至少执行一次真实 DeepSeek 上传编译和一次真实带引用问答。

- 预置 seed 验收不调用 DeepSeek，但必须通过正式后端导入并完成来源、知识、关系、证据与图谱对账。
- 本地模型连接不属于 MVP 验证项；验收的是其前端状态真实说明、无假操作和双主题完成度。

### 12.3 视觉门槛

- 知识问答：流式阶段、引用聚焦、来源高亮/展开、错误恢复、推荐问题和最近对话完整。
- 资料管理：66 个内置来源可见、Markdown 可读、上传与任务阶段连续、部分失败可恢复。
- 知识页面：长文排版、目录、表格、代码、引用和来源定位在两套主题均清晰。
- 知识图谱：150 节点/450 关系对账；非白屏、非过曝、不发虚；光效、关系粒子、相机聚焦和详情联动有效。
- 设置：DeepSeek 与 OpenAI 兼容服务的未配置、测试中、可用和失败状态真实，切换当前配置有效；本地模型明确未接入；主题切换不重置业务状态。
- 品牌：展开/收起侧边栏、浏览器标题和启动状态使用完整标准名称与批准标志；实际存在的署名逐字匹配标准文案。
- Playwright 运行期间浏览器控制台不得出现未处理错误，网络失败不得被 UI 显示为成功。

## 14. 实现阶段 Definition of Done

MVP 进入完成状态必须同时满足：

- 内置 Markdown 作为 66 个逻辑来源、72 个来源版本真实出现在资料管理，并可安全阅读；
- 默认快照 150 个知识项、450 条关系和 1112 个证据片段经后端正式导入且可逐项追溯；
- 用户上传 Markdown 能真实创建来源版本、调用 DeepSeek、显示持久化编译阶段、接受并发布新快照；
- 知识页面、图谱、检索、推荐问题和问答只消费当前已接受快照；
- 两条在线配置分别可保存和真实测试，切换后编译与问答使用当前配置，密钥不泄露；
- 本地模型只呈现明确的未接入前端状态，没有后端请求、假连接、假保存或假成功反馈；
- 除本地模型连接外，不存在前端生成的业务结果、硬编码图谱、固定答案、假进度、死按钮或隐藏数据路径；
- 明暗两套主题下的六个一级模块、图谱效果、问答引用效果和跨页面状态连续性通过验收；
- 用户可见产品名、标志、浏览器标题和实际存在的署名符合 `docs/design/brand.md`；
- 后端测试、前端测试、Playwright 核心旅程、内置数据校验、构建与静态检查全部通过；
- README 和 AGENTS.md 中记录的命令与实际工程一致，不包含尚不存在的命令。
