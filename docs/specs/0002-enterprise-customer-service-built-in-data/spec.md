## 2. 目的

本数据集同时服务于资料上传、知识编译、知识页面、知识图谱和带引用问答。
它用于提供首次进入即可观察的完整产品效果，也用于后续 DeepSeek 真实上传编译链路的回归验收。

预置知识快照由 Codex 从本数据集的 Markdown 来源预编译。它不是独立手写图谱：

- 每个知识项保留稳定 `knowledgeId` 和来源版本；
- 每条关系保留 `relationId`、方向、语义和证据；
- 每个证据片段保留 `evidenceId`、来源版本、文件路径和字符范围；
- 图谱只是同一知识快照的派生投影；
- 后续 DeepSeek 编译必须产出同一对象契约，并由相同产品读取路径消费；
- 预置数据不得绑定固定问答答案或绕过正式知识服务。

## 4. 八个展示领域

1. 项目与角色；
2. 商品与库存；
3. 订单与支付；
4. 履约与售后；
5. 客户服务；
6. 知识与模型；
7. 系统与接口；
8. 质量、安全与运营。

领域只用于图谱颜色和分组。知识类型和关系语义保持独立，不得为了配色改写业务含义。

## 5. 目录与所有权

```text
fixtures/enterprise-customer-service/
├── corpus-manifest.json       # 来源版本清单和 SHA-256
├── rules/                     # 知识类型、关系与编译规则
├── raw/base/                  # 60 份基础来源，只读
├── raw/update-01/             # 12 份新增来源版本，只读
├── reference/wiki/            # Codex 编译的可读互链知识页
├── preset/                    # 可由产品正式数据入口加载的预置快照与图谱投影
├── evaluation/                # 标准问题和机械验收指标
└── tools/                     # 数据集生成与校验工具，不属于产品运行时
```

`raw/` 属于来源层，生成并校验后冻结。`reference/`、`preset/` 和 `evaluation/` 都是可再生产物，
不得反向改写来源。

## 6. 来源文档要求

- 原始资料是正常业务 Markdown，不包含预计算节点、边 JSON 或固定回答。
- frontmatter 只承载来源身份、文档类型、版本、日期、责任方和状态。
- 文档正文包含定义、流程、规则、异常、验收和相关资料编号。
- 文档之间允许显式引用稳定资料编号，以表达企业文档之间的依赖关系。
- 基础文件正文不少于 800 个字符；更新文件必须明确旧值、新值、生效范围和回滚条件。
- 内置资料不包含现实企业、客户、订单、联系方式、访问凭据或个人身份信息，
  其中的业务规则只作为本产品知识内容，不构成任何外部企业承诺。

## 7. 编译契约

Codex 参考编译和后续 DeepSeek 运行时编译都必须输出：

1. `SourceVersion`；
2. `EvidenceFragment`；
3. `KnowledgeItem`；
4. `Relation`；
5. `KnowledgeSnapshot`；
6. `GraphProjection`。

参考 Wiki 按知识单元而不是来源文件划分。所有 wikilink 使用带目录前缀的
`[[domain/slug]]`，并且每个目标页面真实存在。

## 8. 预置与实时编译边界

```text
仓库 Markdown ──Codex 预编译──> 预置 KnowledgeSnapshot ──> 正式产品读取路径

用户上传 Markdown ──DeepSeek 编译──> 新 KnowledgeSnapshot ──> 同一正式产品读取路径
```

两条入口允许使用不同模型，但不得使用不同对象模型、不同图谱语义或不同问答引用逻辑。

## 9. 开发接入基线

- 默认描述文件固定为 `fixtures/enterprise-customer-service/preset/default.json`；
- 默认描述文件必须解析到 `KS-RETAIL-SERVICE-1.1`、`knowledge-snapshot-v1.1.json` 和
  `graph-projection-v1.1.json`；
- `KS-RETAIL-SERVICE-1.0` 作为可追溯历史快照保留，用于增量编译和旧值防线验收；
- 初始化器必须先通过与用户上传共用的正式来源 service/repository 导入 66 个逻辑来源和
  72 个不可变 Markdown 来源版本；资料管理必须显示来源、版本、状态并允许只读打开正文；
- 产品只能通过正式数据接入边界导入默认快照，页面不得各自直接加载预置 JSON 形成第二套状态；
- 预置快照只在内置知识项目尚未创建时导入一次，不得在每次启动时覆盖用户产生的当前快照；
- 图谱投影、Wiki 页面、来源证据、推荐问题和问答检索均由同一 `snapshotId` 关联；
- 后续用户上传 Markdown 必须真实调用 DeepSeek 编译并产出第 7 节对象，调用与验证边界遵循
  `docs/architecture/0001-lmvk-mvp-technical-plan.md`；
- 标准问题和其中的预期要点仅用于评测，不得被产品运行时按问题文本命中并直接返回。

## 10. 验收

- 来源数量、知识数量和关系数量符合第 3 节；
- 原始 Markdown 的 SHA-256 与清单一致；
- 每个知识项至少有一个来源，每条关系至少有一个证据；
- 关系端点、证据来源和 wikilink 均无悬空；
- 图谱投影与知识快照节点、关系数量逐项一致；
- 展示领域不超过 8 个，节点 degree 由真实关系计算；
- 基础快照与更新快照身份连续，更新不会覆盖历史来源版本；
- 标准问题只作为评测输入，不成为产品固定答案分支。
- `preset/default.json` 指向 `KS-RETAIL-SERVICE-1.1`，默认快照与图谱投影分别为 150 个知识项/节点和 450 条关系/边；
- 默认快照包含 72 个来源版本和 1112 个证据片段，且每个身份均能回到清单中的 Markdown 来源；
- 资料管理实际显示 66 个逻辑来源并可对账 72 个来源版本，抽查当前和历史 Markdown 版本均可使用正式来源阅读器打开；
- `node fixtures/enterprise-customer-service/tools/validate-fixture.mjs` 执行通过后，数据集才可作为开发基线。
