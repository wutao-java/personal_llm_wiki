# 三元选型：传统 RAG / 编译式 wiki / GBrain

## 何时使用

面对一个知识库或 RAG 需求，要在三条范式间选型时：传统向量 RAG（机器索引）、编译式 wiki（可读知识网络）、
GBrain（self-wiring 知识图谱 + 综合层）。选错的代价是"为省成本误选编译式（其实更贵）"或"小问答上重型图谱"。

## 核心决策树

按需求的**主诉**分流，不要按"哪个先进"选：

1. 只要机器召回、不需人读/治理、语料量大、追求便宜快 → **传统向量 RAG**。
   - 组织成机器索引（黑箱），切块 + embedding + top-k。成本最低。

2. 要可读、可审计、可人工治理、跨源冲突要显性化 → **编译式 wiki（LLM Wiki）**。
   - 组织成人可读的互链 wiki，一次编译多次命中。
   - 成本直觉：编译式**单次查询约 20 倍 token** 于向量 RAG——它买的不是省钱，是**可治理性**（可审计、可沉淀、冲突可见）。拿"省成本"当选它的理由就是选错。

3. 要实体/关系图谱、backlinks、时序综合（find_trajectory）、跨会话记忆 → **GBrain 图谱**。
   - self-wiring 解析人写的 wikilink 建图（零 LLM）+ 检索层（HNSW 向量 + BM25 + RRF 融合）+ 综合层（`think` 多页综合成带引用答案 + Gaps 空白分析）。
   - 检索选择：需精确关键词命中用 BM25，需语义/跨语言用向量，默认混合（RRF 给两路平权）。只要页面清单用 `search`；要综合成答案用 `think`。

**GBrain vs GraphRAG 的区别轴 = 构图方式**：GBrain 解析人写好的 `[[链接]]`（self-wiring，零 LLM、可溯源）；GraphRAG 用 LLM 抽实体建图。要"人可治理、可审计"选前者。

## 选型校验（下结论前过一遍）

- [ ] 选编译式/GBrain 的理由是"可治理/可综合"，不是"省成本"——成本上它们更贵。
- [ ] 成本贵 ≠ 质量差：贵是买治理与综合能力，别用成本单轴否定。
- [ ] 引 benchmark 时**不混引两套跑分**（如 BrainBench 有自身 caveat）——不同 benchmark 口径不可拼在一起下结论。
- [ ] 语料规模与查询频次匹配方案：一次性小问答别套 GBrain 全家桶（过度工程）。

## 反模式

- ❌ 拿"省查询成本"当选编译式 wiki / GBrain 的理由——实测约 20 倍 token，它更贵，理由应是可治理。
- ❌ 混引两个不同 benchmark 的分数拼出结论——口径不一致，严禁混引。
- ❌ 小规模一次性问答上 GBrain self-wiring + 向量 + 综合全链路——过度工程，传统 RAG 就够。
- ❌ 把 GBrain 当"更好的 GraphRAG"无脑替换——区别在构图方式，需求不对口反而更复杂。
