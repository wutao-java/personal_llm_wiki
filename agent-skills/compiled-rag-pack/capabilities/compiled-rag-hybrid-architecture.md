# 混合架构：编译式 wiki + 向量 RAG 并用

## 何时使用

知识里**同时存在稳定核心层**（架构设计/规格/政策，写定长期不变）**和易变长尾层**（工单/changelog/会议纪要/事故报告，每天演变），
且单源 GBrain 已被"易变数据重编译成本"逼到墙角时——让两套系统各管一摊、前置路由分流、跨系统融合。**先用单源跑通、确认不够，再上混合**（否则过度工程）。

## 核心决策：该不该上（按顺序自问，任一"否"即停）

1. 知识**真的同时有稳定层和易变层**？（稳定设计文档 + 每天新增工单/日志）否 → 单 GBrain 足够。
2. 单源 GBrain 跑通了、**真被易变数据重编译成本逼到墙角**了？没有 → 先用单源。
3. 能承受**路由复杂度**这个核心代价？（路由错比单源更难调试——要先分清是检索错还是路由错）承受不了 → 别上。

三条都"是"再上。**混合不是免费的更好**：它换来的是跨界综合型查询上"同时拿到 wiki 权威稳定设计 + RAG 近期事实"的质量底线和可溯源，**代价是路由复杂度**——别指望它总召回率碾压单源。

**给方案时必须先把成本账讲明**（用户常带着"混合=省钱"的误解来）：编译式查询约 21 倍 token 于向量 RAG
（≈165 万 vs 约 7.9 万）——把易变数据路由去 RAG 的理由是**重编译成本高 + 突破编译式规模天花板**，不是省 token。

## 落地流程（四环节）

**环节 1 · 双源建库**
- wiki 侧：你熟的 `gbrain init/import/doctor`，导入足量稳定知识（示例 60 页四类目录 architecture/api-specs/team/policies，`[[wikilink]]` 互链）。
- RAG 侧：ChromaDB `PersistentClient` 本地持久化，自定义 embedding function 打 DashScope 兼容端点。
- [ ] **两条几何前提**（融合能成立的地基）：双源用**同一个 embedding 模型**（示例都 `text-embedding-v3` 1024 维）+ **同一个产品域**（`product_domain` 一致）——否则向量不在同一空间、分数不可比、业务不同域。
- [ ] 验收：同一个词（如 `token`）分查两源，wiki 返回稳定 policy/architecture 页、RAG 返回易变工单/changelog 条目 = 互补成立。

**环节 2 · 查询路由器（灵魂，也是复杂度来源）**
- 三层逻辑：LLM zero-shot 三分类（主路径）→ 关键词规则兜底 → 默认 `both`（双查保召回，误判不致命）。
- 三类映射：稳定核心型→`wiki`、易变长尾型→`rag`、跨界综合型→`both`。
- [ ] **路由质量高度依赖两源描述文案**——把 `wiki_description`/`rag_description` 写准（准确刻画各覆盖哪类知识）是你最该上心的地方。
- 边界要诚实：zero-shot 路由准确率高度依赖测试集措辞分布（实测同一路由器 11/11=100% 与 6/9=66% 两组都真实）；**跨界 query 措辞偏向某源时会被判到那源**。彻底解法是 query decomposition（拆成 wiki+rag 子查询），成本高、作进阶方向。

**环节 3 · 双路检索 + 架构级 RRF 融合 + 来源标注**
- wiki 路：`gbrain query --no-expand`（必加 `--no-expand` 防多查询把 CPU 跑挂；用 `perl -e 'alarm 30'` 或 `timeout` 包装、不走管道）。
- RAG 路：先自算 1024 维向量，`collection.query(query_embeddings=[...])`——**不要用 `query_texts`**（会触发 ChromaDB 内置 384 维 MiniLM，报维度不匹配）。
- 架构级 RRF（第二层，异于大脑内 RRF）：`score = Σ 1/(k_const + rank)`，`k_const=60`（Cormack & Clarke 2009）。**用 rank 不用 score**，因为 wiki 相关度分与 RAG 向量 distance 量纲不可比，排名绕开跨系统归一化难题。
- [ ] 每条结果标 `source_system`（wiki/rag）= provenance，补回编译式在可溯源上的短板。

**环节 4 · 端到端混合问答**
- 融合 top-k（含来源标注）喂 LLM 合成，**要求模型对每段标来源系统**（`[来自 wiki]`/`[来自 RAG]`），工业级可溯源不能省。

**校验环（融合逻辑必须覆盖三降级分支）**：两路都有→正常融合；某路 0 结果→降级单路 + 文档化说明（跨域查询在生产很常见，wiki 路 BM25 跨域 0 命中是预期分支）；两路都 0→落"双源此项为空"。

## 反模式

- ❌ 把混合架构当"省钱方案"——真实数字编译式查询约 **21 倍 token**（≈165 万 vs 向量 RAG 约 7.9 万，arxiv 2605.18490）。路由易变数据去 RAG 的理由是"重编译成本高 + 突破编译式规模天花板"，不是省 token。
- ❌ 双源用不同 embedding 模型或不同产品域——向量不在同一几何空间、分数不可比，融合既不可比也无业务意义。
- ❌ 融合层用原始 score 归一化跨系统分数——量纲不可比，必须用 rank-based RRF。
- ❌ 不实现"某路 0 结果"降级分支——跨域查询触发 BM25 0 命中时会崩或给空答案。
- ❌ 没跑通单源就直接上混合——多一套系统就多一份路由/融合/调试负担，先证明单源不够。
